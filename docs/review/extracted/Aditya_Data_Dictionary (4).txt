A19=Rules for every stage
A20=Rule | B20=Why
A21=Never store the secret key in the database or in code | B21=If the key sits next to the hashes, the HMAC gives no protection.
A22=One key per purpose | B22=OTP key, PAN key and email-index key are different, so one leak does not expose everything.
A23=Normalise before hashing | B23=PAN: trim + uppercase. Aadhaar: digits only. Email: trim + lowercase. Phone: E.164. Otherwise the same value gives different hashes.
A24=Add a purpose prefix | B24=Hash 'pan:ABCPX1234K', not 'ABCPX1234K', so values from different fields can never collide.
A25=Store a key version | B25=hash_key_version tells which key made the hash, so keys can be rotated safely.
A26=Compare in constant time | B26=Use crypto.timingSafeEqual (Node) when checking an OTP, so timing does not leak the code.
A27=Never log plain values | B27=No OTP, PAN, Aadhaar, email or phone in logs or error messages (base file: audit metadata excludes contact data).
A28=Limit attempts | B28=Hashing protects stored data; attempt limits protect the live check. Both are needed.
A29=Prefer not storing at all | B29=The safest Aadhaar is the one you never store: masked value + provider token only.
